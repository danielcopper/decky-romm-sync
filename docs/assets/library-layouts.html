Tender Library Layouts #1815 · panel 854 px wide, 454 px tall on the Deck

LAYOUT
Width
The panel is 854 px and the content 806 px — the same on every display. On the Deck that is the whole screen; on a desktop Big Picture window the library stays visible beside it. Nothing here needs to be responsive in width.
Height
The scarce axis. On the Deck the panel is 454 px and the page's body about 263 px after the title bar, Back, the page title and the tab row. A taller window simply gives the two regions more rows. Every layout below is drawn at the Deck's height — the worst case.
Navigation
Focus selects in a list, A works the control in the row, L1/R1 switch the tabs, and a row must be focusable to be reachable at all.

Notes

  1. 1

    Two groups, frozen order. Synced above Available, alphabetical inside. Toggling a row does not move it while the page is open. The row carries the BIOS state as a number — 3 / 5, 0 / 2, a dash where the platform wants none — so the colour only reinforces it. The toggle in the row is the only sync control: focus is already there and A works it, so the detail does not repeat it.

  2. 2

    Core. One row that opens the same context menu the System page uses today. Needs the new per-platform read.

  3. 3

    BIOS as a table. Wanted · On disk · Contents, Download on a missing row. Contents stays empty until #1803's backend half exists.

  4. 4

    Remove last. The two actions from today's platform modal, red, confirmed.

What it costs

  • Only about four rows of the detail are visible at the Deck's height; core, BIOS and Remove are a scroll away.
  • Every fact about a platform is in one column, so nothing competes for width.
  • You see one platform's state at a time — comparing two means walking the list.

B · Detail with a header

Same two columns, but the detail's top is one compact header line instead of three stacked sections — so the BIOS table, the part with the most rows, starts near the top.

Notes

  1. 1

    One header line carries the name, the counts, the core and the BIOS state. Core and Remove become two buttons instead of two sections. The sync toggle stays in the list row, where the focus already is.

  2. 2

    The BIOS table gets the space, which is the only part of a platform with a variable number of rows. Contents is #1803's column: whether the file on disk is the right one. Its backend half does not exist yet — the vendored resolver can verify, the plugin asks it not to — so every row reads a dash until that lands.

  3. 3

    The two removals are named and sit last, under the BIOS buttons, red. Reaching them takes a scroll, which is right for what they do.

What it costs

  • Changing the core moves behind a press. The core is readable in the header but not changeable there.
  • Denser header — four facts on one line at 526 px.
  • A platform with no BIOS at all shows a nearly empty pane.

C · One wide table

No detail pane. Every platform is a row across the full width with its facts as columns, and A opens the focused row in place.

Notes

  1. 1

    Everything at a glance. Core and BIOS state are columns, so you compare platforms without walking them one by one.

  2. 2

    A opens the row in place — actions as a button row, then the BIOS files. Closing it restores the list.

What it costs

  • Height is the scarce axis and this spends it twice: the open row plus the rows below it. At 263 px you see the open platform and about two others.
  • The core label is needed for every visible row, not just the focused one — with a per-platform read that is one call per row.
  • Six columns at 806 px means a truncated core name on the longer ones.
  • It is the layout closest to today's System page, which the redesign set out to replace.

Recommendation B. The two differ in one thing: what the top of the detail costs. A spends four rows on a name line and a core section, so the BIOS table starts below the fold; B spends one line on name, counts, core and BIOS state, and the table fits whole. Everything else — the list, the navigation, one core read per focused platform — is identical. A stays right if changing the core should be a visible row rather than a button.
